*sshdev.txt*	Edit remote projects with your local Neovim config, over SSH.

Author: mistgc and sshdev.nvim contributors     MIT licensed    *sshdev*

==============================================================================
INTRODUCTION						*sshdev-intro*

A local Neovim UI is attached to a remote `nvim --headless --listen`
server through an SSH port forward: >

	local UI / --remote-ui client  <->  ssh -N -L  <->  remote nvim --listen

The remote state is split into two levels:
							*sshdev-nvim-profile*
	nvim profile	a REUSABLE bundle of the uploaded config + the plugin
			instances + a link to one nvim release:
			  <remote_root>/nvim-profiles/
			    --<local-hostname>--<nvim-version>--<hash8-config-content>--
			The key is derived from the local hostname, the nvim
			version and the CONTENT hash of the uploaded config,
			so it is stable across `touch` and reused by every
			workspace that shares the same config. Plugins are
			installed once per profile.

							*sshdev-workspace-profile*
	workspace profile
			the per-(client machine, workspace) runtime state:
			  <remote_root>/workspace-profiles/
			    --<local-hostname>--<workspace-path>--/
			It holds session.vim, the port-forward list forward.txt
			(see |sshdev-forwards|), server pid/address/log and a
			relative symlink `nvim-profile` to the nvim profile.
			The key uses the LOCAL hostname so several client
			machines sharing one remote account stay isolated.

							*sshdev-workspace*
	workspace	the remote PROJECT DIRECTORY the server runs in,
			e.g. "~/src/app".

What sshdev.nvim does for a workspace:

1. Ensures a Neovim release matching your local version exists under
   `<remote_root>/nvim-bins/<nvim-version>/` (downloading through `proxy` /
   `download_mirror` if configured). The nvim profile links to it with
   `nvim-bin -> ../../nvim-bins/<nvim-version>`.
2. Uploads |stdpath()|'s "config" into the nvim profile, respecting
   `excludes`, and runs a headless install ONCE per config content hash.
3. Reuses that nvim profile for every other workspace with the same config:
   no config upload and no plugin install.
4. Starts a detached server in the workspace, forwards it, and attaches.
5. Persists the session per workspace: the server writes
   `<workspace-profile>/session.vim` when it exits and restores it on the next
   start. There is no quit hijacking -- |:q| behaves normally.

Requirements: Neovim >= 0.12 locally (:connect was added in 0.12), ssh/scp
(OpenSSH >= 7.6), POSIX remote (Linux/macOS) with tar and curl. Key-based
authentication is recommended; hosts that only accept passwords are
handled automatically (key first, password fallback — OpenSSH client
>= 8.4, see |sshdev-auth|).

COMMANDS						*sshdev-commands*

*:SshDevConnect*
:SshDevConnect[!] [{dest}] [{workspace}] [--nvim-profile={key}] [--auth={mode}]
	Connect (bootstrap + attach).
	Without arguments, opens the connection picker (telescope when
	installed, |vim.ui.select()| otherwise) with the remembered
	connections plus a "new connection" entry; a new connection also
	offers the remote nvim profiles for reuse.
	{dest} is a destination "[user@]host[:port]" or a key from
	`remotes`; defaults to `host`. {workspace} is the remote project
	directory (default: `workspace`, then the remote $HOME).
	--nvim-profile={key} creates/repoints the workspace to an EXISTING
	nvim profile instead of the auto (config content derived) one. The
	profile is used as-is; its config and plugins are not overwritten.
	--auth={mode} overrides `auth` for this invocation: "auto"
	(key first, password fallback), "password" (ask via |inputsecret()|
	before the first ssh call) or "key" (strictly non-interactive).
	See |sshdev-auth|.
	With !, a running server is stopped and the config/plugins are
	reinstalled into this config's own (auto) nvim profile.

*:SshDevAttach*
:SshDevAttach [{dest}] [{workspace}]	Attach to a RUNNING server (no
	bootstrap). Fails if no server is running for the workspace profile.

*:SshDevInstall*
:SshDevInstall [{dest}] [{workspace}] [--nvim-profile={key}]
	Bootstrap only: binary, nvim profile (config + plugins), workspace
	profile. Does not start or attach.

*:SshDevSync*
:SshDevSync [{dest}] [{workspace}]	Re-upload the config and reinstall the
	plugins into this config's own nvim profile. Use :SshDevConnect! to
	restart the server with the new config. Never overwrites an
	explicitly reused profile (the auto profile is synced instead).

*:SshDevStop*
:SshDevStop			Stop the remote server (SIGTERM, so it saves
	session.vim) and kill the local tunnel.

*:SshDevStatus*
:SshDevStatus			Report local host, auto nvim profile key,
	active session, workspace/nvim profiles, tunnel, remote server and
	saved-session state.

*:SshDevHistory* *sshdev-history*
:SshDevHistory [{dest}]		Open the workspace picker: scans the remote
	`workspace-profiles` whose `client-host` equals this machine's local
	hostname (user isolation), merges the local history and reconnects to
	the selected workspace using its recorded nvim profile key.

*:SshDevProfiles*
:SshDevProfiles [{dest}]	List the reusable nvim profiles that exist on
	the remote for this client host: key, nvim version, ready state and
	the number of workspace profiles referencing them.

*:SshDevForward*
:SshDevForward [{dest}] [{workspace}]
	Edit the port forwards of a workspace: opens its
	`<workspace-profile>/forward.txt` (fetched into a local buffer; an
	all-commented template is created when the file does not exist
	yet). One forward per line: >
	    3080 = 127.0.0.1:3080
	    8080 = 127.0.0.1:8080
<	forwards THIS client's 127.0.0.1:3080/8080 to the SERVER's
	127.0.0.1:3080/8080. SAVING the buffer re-uploads the file to the
	workspace profile and replaces the running forwards: one detached
	`ssh -N` carries a `-L` per line (loopback-bound; the target may
	be any host the SERVER can reach, e.g. `5432 = db.internal:5432`).
	`#`-lines and blank lines are ignored; an empty file stops all
	forwards. Invalid lines are reported with their line numbers and
	change nothing. Without arguments the ACTIVE session's workspace
	profile is used; [dest] [workspace] resolve it like
	:SshDevConnect. Inside the ATTACHED remote session the command
	opens the same file in the attached UI and every save is applied
	client-side over an RPC control channel (see |sshdev-forwards-attached|).
	See |sshdev-forwards|.

*:SshDevEnv*
:SshDevEnv [{dest}] [{workspace}]
	Edit the environment variables of a workspace: opens its
	`<workspace-profile>/env.txt` (fetched into a local buffer; an
	all-commented template is created when the file does not exist
	yet). Strict format, one variable per line: >
	    KEY=VALUE
	    DATABASE_URL=postgres://127.0.0.1:5432/app
<	The value is everything after the first "=", used verbatim (no
	quote stripping, no $VAR expansion). "#"-lines and blank lines are
	ignored. SAVING the buffer re-uploads the file and injects the
	variables: every ssh-run script exports them, and a running server
	gets them through the RPC control channel (vim.env). Invalid lines
	are reported with their line numbers and change nothing; duplicate
	keys and the keys sshdev reserves (SSHDEV_*, XDG_*, NVIM_APPNAME,
	SSH_ASKPASS*, HOME) are rejected. Without arguments the ACTIVE
	session's workspace profile is used; [dest] [workspace] resolve it
	like :SshDevConnect. Inside the ATTACHED remote session the command
	opens the same file in the attached UI; a save applies on the server
	and refreshes the client over the control channel (see
	|sshdev-env-attached|). See |sshdev-env|.

*:SshDevLog*
:SshDevLog			Open the sshdev log buffer.

Telescope (optional): >

	:Telescope sshdev connections
	require('telescope').extensions.sshdev.connections()
<
	`<C-d>` in the picker forgets the highlighted connection.

==============================================================================
REUSING AN NVIM PROFILE					*sshdev-reuse*

`nvim_profile = "auto"` (the default) derives the key from
(local hostname, nvim version, config content hash):

	* editing the config -> new key -> a fresh one-time install
	* |touch|ing files   -> same key -> no reinstall
	* a NEW workspace with the same config -> the existing nvim profile
	  is reused: no scp, no plugin install

To reuse a profile installed from another config state (e.g. pin a project to
the plugins it was created with), pass its key: >

	:SshDevProfiles me@myhost
	:SshDevConnect me@myhost ~/src/second --nvim-profile=--laptop--v0.12.6--1a2b3c4d--
<
The reused profile is immutable: sshdev never uploads the current config into
it. If the key does not exist or never finished installing, sshdev warns and
falls back to the auto profile.

`:SshDevConnect` without arguments offers the same choice interactively after
you typed the destination and workspace.

==============================================================================
SESSION PERSISTENCE					*sshdev-session*

The remote server saves its Neovim session to
`<workspace-profile>/session.vim`:

	* on VimLeavePre (:q, :wq, :cquit, SIGTERM from :SshDevStop, ...)
	* on FocusLost / VimSuspend (best-effort snapshot)

and restores it on the next start (VimEnter), so reconnecting brings back
buffers, windows and layout. |:q| therefore behaves normally -- the server
exits and the session is preserved for the next connection.

Session sourcing reads the buffers with the ordinary read events
suppressed, so sshdev explicitly re-establishes `FileType` on them: once
right after the restore, and again shortly after the first UI attaches
(when lazy-loaded plugins have registered their handlers). Without this,
restored buffers would show no syntax highlighting, treesitter or LSP.

Sessions are per workspace; plugins/state are per nvim profile, so two
workspaces can share a config and still keep independent sessions.

Configure with `session` (save/restore on/off) and `restore_session`
(start clean while still saving). SIGKILL cannot be handled.

==============================================================================
ATTACHING						*sshdev-attach*

Since Nvim 0.12, running `nvim` starts a builtin UI client process plus an
embedded server, and that UI client implements the "connect" UI event. So
|:connect| re-attaches the terminal UI in place: >

	:connect 127.0.0.1:<port>

The address must be a bare "host:port" (or the |ssh://| builtin remote-ssh
form). A "tcp://host:port" URI is NOT a valid nvim server address: the UI
detaches first, the attach fails, and the process ends -- which makes
|:connect| look unsupported. (:connect was added in 0.12; 0.11 only has
|:detach|.)

`attach` selects the strategy:

	"auto"      (default) |:connect| when the command exists (>= 0.12);
	            headless -> "command"
	"connect"   always |:connect| "127.0.0.1:<port>"
	"terminal"  open a terminal tab running a separate UI client:
	            nvim --server 127.0.0.1:<port> --remote-ui
	            (keeps the local nvim alive while working remotely)
	"command"   do not attach; just report the command to run

RECONNECTING					*sshdev-reconnect*

A direct |:connect| channel is the UI client's *server* channel: when the SSH
tunnel dies (network flap, VPN reconnect, laptop suspend), the UI client gets
EOF and nvim exits the whole local process. `reconnect` (default on) avoids
that by attaching through a small local relay instead of directly into the
tunnel: >

	local UI  --:connect-->  127.0.0.1:<port>   [reconnect proxy]
	                            |  owns: ssh -N -L <ui> -L <control>
	                            v
	                     remote nvim --headless --listen

The UI client's channel is the relay's local socket and never closes. When
the tunnel dies the relay rebuilds it (same local ports, retried with backoff
while the network is down), reconnects to the remote server and replays the
UI attach there. The remote server sees a new UI attach and sends a full
screen; the local UI just gets a normal redraw. The remote server and its
session are untouched, so the next screen is exactly where you left off.

The local nvim server is detached by |:connect| and keeps running headless;
it re-opens the RPC control channel after the reconnect and re-applies
forward.txt / env.txt (|sshdev-forwards|, |sshdev-env|).

Limits:
- detection waits for ssh itself: up to ServerAliveInterval *
  ServerAliveCountMax (45 s with the built-in options), usually instant when
  the TCP connection is reset. The terminal title shows
  "sshdev: reconnecting to …" meanwhile; keys typed while frozen are
  discarded, not replayed.
- a reconnect only re-establishes the LINK. If the remote server stopped
  (|:q|, :SshDevStop, host reboot) the local UI exits as before; reconnect
  later with :SshDevConnect.
- the `terminal` attach strategy has its own UI client and is not supervised.
- `reconnect = false` restores the plain |:connect| behaviour.

PORT FORWARDS						*sshdev-forwards*

`:SshDevForward` manages custom ssh port forwards for a workspace. The
forward list is per-(client, workspace) state, so it lives in the REMOTE
workspace profile, next to session.vim: >

	<remote_root>/workspace-profiles/--<host>--<ws-path>--/forward.txt

Format -- one forward per line: >

	<local-port> = <remote-host>:<remote-port>
	3080 = 127.0.0.1:3080
	8080 = 127.0.0.1:8080

The local side binds 127.0.0.1 on THIS machine; the target address is
resolved on the SERVER, so "127.0.0.1" is the server itself and
"db.internal:5432" reaches hosts only the server can see. `#`-lines and
blank lines are ignored. IPv6 target literals are not supported (the
same limitation as destinations, |sshdev-commands|).

Editing happens on a local mirror under
|stdpath()|'s "cache"/sshdev/forward/<workspace-profile-key>/forward.txt:
the command fetches the remote file (creating an all-commented template
when it does not exist yet) and opens it in a split. SAVING the buffer
(:w) runs the apply pipeline:

	parse ─► scp back to the workspace profile ─► kill the previous
	forward tunnel ─► start ONE detached `ssh -N` carrying a `-L`
	per line, then WAIT until the tunnel verifiably accepts
	connections (ExitOnForwardFailure: a bind ssh cannot do -- a
	busy port, a Windows reserved range, a rejected auth -- kills
	the process).

	* invalid lines are reported with line numbers; NOTHING is applied
	  (the remote copy and the running forwards stay unchanged)
	* when the new tunnel dies on start, the PREVIOUS set is restored
	  and ssh's own error is reported -- a bad save never leaves the
	  workspace without its working forwards
	* an empty / comment-only file stops all forwards
	* re-saving restarts the whole set atomically (one ssh process)
	* the buffer stays open: edit again and :w re-applies

The forward tunnel is stopped by :SshDevStop and when the local nvim
exits (like the session tunnel; it survives a |:connect| that keeps the
local instance alive as a UI client). forward.txt persists remotely, so
re-establishing after a restart is one :SshDevForward + :w away.

Reconnecting re-applies them for you: with `forward_on_connect`
(default on) every :SshDevConnect / :SshDevAttach re-reads the
workspace's forward.txt and re-starts its forwards automatically --
no editor round trip needed. Forwards that are already listening
(a leftover from the previous session) are kept and reported as such;
force a clean re-apply with :SshDevForward + :w.

Forwards do not depend on the nvim server: they work whether or not one
is running, and with password authentication they use the same masked
askpass mechanism as the tunnel (|sshdev-auth|).

INSIDE THE ATTACHED SESSION					*sshdev-forwards-attached*

With the default "connect" attach, commands typed after
|:SshDevConnect| run in the REMOTE nvim -- and `:SshDevForward` works
there too: the forward file lives on that host, so it opens in the
attached UI, and every save is pushed to the CLIENT over an RPC control
channel that the client opened at attach time
(`SSHDEV_CONTROL_CHANNEL` on the remote). The client (headless behind
the attached UI) re-reads the file, replaces the forward tunnel and
reports the outcome back into the attached UI -- the whole loop stays
in one editor. The fallback, when the control channel is unavailable
(e.g. the client runs an older plugin): >
	:detach		exits the UI (the server keeps running)
	<SshDevForward + :w in a NEW local nvim>
	:SshDevAttach	return to the session
<
Note that while the UI is attached, the local nvim process IS the
remote's UI client: when it exits, the forwards and the tunnel keep
running detached. A save from a NEW nvim then reports their ports as
busy until the leftover ssh is killed ("netstat -an" / "ss -ltn" show
the pid), or until :SshDevAttach reuses the session.

Local listeners bind loopback only -- nothing is exposed to the network.

ENVIRONMENT VARIABLES					*sshdev-env*

`:SshDevEnv` manages custom environment variables for a workspace. Like
forward.txt, the list is per-(client, workspace) state, so it lives in the
REMOTE workspace profile: >

	<remote_root>/workspace-profiles/--<host>--<ws-path>--/env.txt

Format -- one variable per line, values verbatim: >

	KEY=VALUE
	NODE_ENV=development
	DATABASE_URL=postgres://127.0.0.1:5432/app
	PATH=/opt/tools/bin:/usr/bin:/bin
<
`#`-lines and blank lines are ignored. A value is everything after the
FIRST "="; spaces, "#" and "=" are kept, quotes are not stripped and
$VAR is not expanded. An empty value is allowed. Duplicate keys and the
keys sshdev needs itself are rejected: `SSHDEV_*`, `XDG_CONFIG_HOME`,
`XDG_DATA_HOME`, `XDG_STATE_HOME`, `XDG_CACHE_HOME`, `NVIM_APPNAME`,
`SSH_ASKPASS`, `SSH_ASKPASS_REQUIRE`, `HOME` (the last one would point a
local ssh child at the wrong config/keys). Invalid lines are reported
with their line numbers; a single bad line means nothing is applied.

Injection points:

	* every remote script sshdev runs is prefixed with
	  `export KEY='value'` lines, so the nvim download, the headless
	  plugin install and the server start all see the variables;
	* the server process inherits them BEFORE your config loads, so
	  `vim.env` reads at startup work;
	* a RUNNING server receives them through the RPC control channel
	  (`vim.env` is updated), so LSPs/terminals/jobs started later
	  inherit them. A process already started (an LSP client) keeps
	  its old environment -- restart it; config-time reads need a
	  server restart (:SshDevConnect!);
	* ssh/scp child processes also get the variables in their local
	  environment (auth keys win). This does NOT forward them to the
	  remote command -- the script prefix above is what the remote
	  side sees.

Saving env.txt uploads it to the workspace profile and applies it. The
remote copy is forced to mode 0600 after every upload (an explicit
remote chmod: scp alone would copy the client's mode, which is 0666 on
Windows). With `env_on_connect` (default on) every
:SshDevConnect/:SshDevAttach re-reads the file and injects it; removed
lines unset the variable at runtime (a server started before this
feature has no key manifest and needs a restart instead).

The local mirror and the remote file are 0600, the buffer uses no
swap/undo file, and values never appear in the log or notifications.

INSIDE THE ATTACHED SESSION					*sshdev-env-attached*

With the default "connect" attach, :SshDevEnv typed in the attached
session opens the env.txt on the SERVER. A save is applied to that
server immediately, then the client is notified over
`SSHDEV_CONTROL_CHANNEL` to refresh its local mirror and active map
(which later ssh/scp commands use). When the control channel is
unavailable the file still applies to the server; the client mirror
refreshes on the next :SshDevConnect.

PASSWORD AUTHENTICATION					*sshdev-auth*

`auth = "auto"` (the default) tries key/ssh-agent first, fully
non-interactive. When the server REJECTS that ("Permission denied
(publickey,...)"), sshdev asks for the password once (|inputsecret()|,
masked), retries and keeps it ONLY in memory for the lifetime of the
local nvim session -- never written to disk, history or the log. A
working key keeps working: ssh tries keys first, the askpass helper is
only consulted when a password is actually needed.

Explicit modes: >

	require('sshdev').setup({
	  host = 'me@myhost',
	  auth = 'password', -- ask BEFORE the first ssh call (known
	                     -- password-only host; skips the failed
	                     -- non-interactive round trip)
	  -- auth = 'key',   -- strictly non-interactive: never prompt
	})
<	or per invocation (--auth=auto / --auth=password / --auth=key;
also works for :SshDevAttach, :SshDevInstall, :SshDevSync and the
pickers): >

	:SshDevConnect me@myhost:2222 ~/src/app --auth=password
<
Once a password is in play, every ssh/scp/tunnel spawn receives: >

	SSH_ASKPASS=<stdpath("cache")>/sshdev/askpass.{cmd,sh}
	SSH_ASKPASS_REQUIRE=force
	SSHDEV_PASS=<password>
<	so OpenSSH authenticates without a terminal -- verified also for the
detached `ssh -N -L` tunnel. The helper script is STATIC: it prints
$SSHDEV_PASS and contains no secret, so it may live in the cache dir.

A rejected password ("Permission denied (publickey,password)") drops the
cached entry, so the next :SshDevConnect prompts again.

Requirements / caveats:
	* The first attempt of the "auto" mode (and every "key" mode call)
	  runs with BatchMode=yes: strictly key/agent, failing fast with a
	  "Permission denied (...)" signature when the server wants a
	  password (an ssh without askpass or console would otherwise HANG
	  on the prompt until the command timeout).
	* The fallback needs an OpenSSH client >= 8.4
	  (SSH_ASKPASS_REQUIRE); the Windows inbox client has it since 8.6
	  (9.5 verified). :checkhealth sshdev reports the capability and
	  the helper status.
	* A headless nvim cannot ask for a password: the connection fails
	  with the original ssh error plus a note (run from a TUI/GUI, or
	  use key auth).
	* The password is visible in the environment of the spawned
	  ssh/scp children (including a tunnel kept alive after nvim
	  exits) -- the accepted trade-off of this mode.
	* Single-factor passwords only: 2FA / keyboard-interactive
	  prompts cannot be answered (use key auth for those).
	* On Windows a "!" in the password cannot be passed (cmd delayed
	  expansion); sshdev warns when it sees one.

REMOTE LAYOUT						*sshdev-layout*

    ~/.sshdev.nvim/
    ├── nvim-bins/<nvim-version>/                 nvim releases (shared)
    │   ├── bin/nvim
    │   └── .platform                             OS/arch marker
    ├── nvim-profiles/--<host>--<version>--<hash8>--/
    │   ├── nvim-bin -> ../../nvim-bins/<version>/  (relative symlink)
    │   ├── nvim-config/                          uploaded config
    │   ├── xdg/share/                            XDG_DATA_HOME (plugins)
    │   ├── xdg/state/  xdg/cache/                XDG state/cache
    │   ├── nvim-version  config-hash  client-host
    │   └── .ready                                install-complete marker
    └── workspace-profiles/--<host>--<ws-path>--/
        ├── nvim-profile -> ../../nvim-profiles/<key>/  (relative symlink)
        ├── nvim-profile.txt  workspace.txt  client-host
        ├── session.lua                           session helper
        ├── session.vim  forward.txt  env.txt  last_used
        └── server.pid  server.addr  server.log

The server runs with `NVIM_APPNAME=nvim-config` and the XDG dirs pointing into
the nvim profile: >

	XDG_CONFIG_HOME=<nvim-profile>
	XDG_DATA_HOME=<nvim-profile>/xdg/share
	XDG_STATE_HOME=<nvim-profile>/xdg/state
	XDG_CACHE_HOME=<nvim-profile>/xdg/cache
<
so the config is `<nvim-profile>/nvim-config` and the plugins live in
`<nvim-profile>/xdg/share/nvim-config/`. State never collides with the remote
user's own nvim or with other profiles.

Bootstrap is atomic: the config is scp'd into
`<nvim-profile>/.staging-<token>/nvim-config`, then one remote script takes a
`mkdir` lock, swaps it in, runs the headless install and writes `.ready` last.
Concurrent connects to two new workspaces serialize on that lock.

The server is located through `<workspace-profile>/server.pid`; if that file is
lost the scripts fall back to matching the unique command line
("<workspace-profile>/session.lua"), so a lost pid file never starts a second
server.

Upgrading from the pre-reuse layout: `<remote_root>/_bin/<version>-<asset>/` is
moved to `<remote_root>/nvim-bins/<version>/` when the asset matches (no
re-download), and an old `session.vim` is copied into the new workspace profile
on first connect. Old plugin trees are not migrated (one fresh install); stop
old servers before upgrading. Old profile directories can be removed once no
longer needed.

SETUP							*sshdev-setup* *sshdev-setup()*

Setup with defaults (all keys optional): >

	require('sshdev').setup({
	  host = 'me@myhost',          -- default destination
	  remotes = { work = 'me@work.example.com:2222' },
	  workspace = '~/src/app',     -- default remote project directory
	  workspace_profile = nil,     -- force the workspace profile dir name
	  nvim_profile = 'auto',       -- "auto" | "--<host>--<version>--<hash8>--"
	  session = true,              -- save <workspace-profile>/session.vim
	  restore_session = true,      -- restore it on start
	  forward_on_connect = true,    -- re-apply forward.txt on (re)connect
	  env_on_connect = true,        -- re-inject env.txt on (re)connect
	  ssh_bin = 'ssh', scp_bin = 'scp',
	  ssh_args = { '-i', '~/.ssh/id_ed25519' },
	  auth = 'auto',       -- "auto" (key first, password fallback) | "password" | "key"
	  remote_root = '~/.sshdev.nvim',
	  nvim_version = 'auto',       -- "auto" | "v0.12.6" | "nightly" | "stable"
	  proxy = 'http://127.0.0.1:7890',
	  download_mirror = 'https://github.com/neovim/neovim/releases/download',
	  install_commands = { 'Lazy! restore' },
	  excludes = { '.git', '.github' },
	  attach = 'auto',             -- "auto" | "terminal" | "connect" | "command"
	  reconnect = true,            -- survive network drops (local relay)
	  history = true,              -- remember connections for the picker
	  history_limit = 50,
	  timeouts = { ssh = 60, download = 600, install = 900, attach = 30, lock = 120 },
	})

host / remotes ~
	`host` is used when :SshDevConnect is called without arguments.
	`remotes` maps names to destinations; its keys complete for
	:SshDevConnect.

workspace ~
	The remote project directory. Absolute or "~/...". The remote nvim
	server's |current-directory| is set to it and it names the workspace
	profile.

workspace_profile ~
	Force the workspace profile directory name. Default:
	"--<local-hostname>--<workspace-path>--".

nvim_profile ~
	"auto" (default) derives the key from (local hostname, nvim version,
	config content hash) and reuses an already installed profile for any
	new workspace. Set an explicit "--<host>--<version>--<hash8>--" key to
	reuse one specific existing profile as-is. `profile` is accepted as a
	deprecated alias for `workspace_profile`.

nvim_version ~
	"auto" (default) installs the release matching your local nvim.
	Dev builds fall back to "nightly" with a warning.

proxy / download_mirror ~
	Both apply to the nvim download ON THE REMOTE host.

install_commands ~
	Extra ex-commands for the headless install run (after your config is
	sourced), e.g. { "Lazy! restore" }.

excludes ~
	Globs matched against paths relative to your config root. They are
	part of the config content hash.

session / restore_session ~
	See |sshdev-session|.

forward_on_connect ~
	Default true: after every :SshDevConnect / :SshDevAttach the
	workspace's persisted forward.txt is re-read (one extra read-only
	ssh round trip) and its forwards re-applied automatically --
	silently does nothing without a forward.txt. Forwards whose ports
	all already listen (leftovers from a previous session) are assumed
	running and kept. Set false to manage forwards purely manually.
	See |sshdev-forwards|.

env_on_connect ~
	Default true: after every :SshDevConnect / :SshDevAttach the
	workspace's persisted env.txt is re-read (one extra read-only ssh
	round trip) and its variables are injected: the start script
	exports them before your config loads, and an already-running
	server gets them over the control channel. Silently does nothing
	without an env.txt. Set false to only inject what an explicit
	:SshDevEnv save loaded for this nvim session. See |sshdev-env|.

attach ~
	See |sshdev-attach|.

reconnect ~
	Default true: the `connect` attach strategy runs through a local
	reconnect proxy that keeps the UI alive when the SSH/network link
	drops, rebuilds the tunnel and replays the UI attach; the remote
	session continues without a restart. The control channel and
	forward.txt are re-applied after the reconnect (see
	|sshdev-reconnect|). Set false to attach directly (a dropped
	channel then exits the local nvim, which is nvim's own behaviour).

auth ~
	"auto" (default): keys / ssh-agent first, non-interactive. When
		the server rejects that, ask for a password once
		(|inputsecret()|, memory only, never on disk), retry and
		cache it for the rest of the nvim session. "password": ask
		before the first ssh call (known password-only host).
		"key": strictly non-interactive, never prompt. The password
		fallback needs an OpenSSH client >= 8.4. See |sshdev-auth|.

history / history_limit ~
	Remembered connections for the pickers, stored in |stdpath()|'s
	"data"/sshdev/history.json. Entries keep the full destination
	including the ssh port plus both profile keys.

timeouts ~
	Seconds: `ssh` per command, `download` for the nvim release,
	`install` for the headless plugin install, `attach` for the tunnel
	and RPC, and `lock` for waiting on another client that is
	bootstrapping the same nvim profile.

==============================================================================
TROUBLESHOOTING					*sshdev-troubleshooting*

:SshDevLog shows scp/ssh output, plugin install output and tunnel messages;
the remote server log is `<workspace-profile>/server.log`.

- "ssh connection failed" -- check key auth works: `ssh <dest> true`.
- "the password was rejected" (password mode or the auto fallback) -- the
  cached entry was dropped automatically; run :SshDevConnect again to
  re-enter it.
- "password fallback unavailable" -- the server rejected non-interactive
  auth AND the password could not be asked (headless nvim, or the entry
  was cancelled). Run from a TUI/GUI, or use key auth.
- Password auth silently not working -- :checkhealth sshdev verifies the
  client supports SSH_ASKPASS_REQUIRE (>= 8.4) and that the askpass
  helper is writable under stdpath("cache").
- Slow FIRST connect -- the nvim release and all plugins are downloaded
  once per remote + config content. Subsequent workspaces reuse the profile.
- The network dropped and the screen froze -- the reconnect proxy is
  rebuilding the tunnel (terminal title: "reconnecting…"); the session on the
  remote host is untouched. If the remote server itself stopped the local UI
  exits instead. See |sshdev-reconnect| and `:SshDevLog`.
- Plugins reinstall unexpectedly -- your config content changed (or the nvim
  version, or `excludes`). The nvim profile key tells you which content it
  belongs to; `:SshDevProfiles` lists them.
- "another sshdev client is still bootstrapping" -- two connects used the same
  new nvim profile; the second waits up to `timeouts.lock` and then asks you to
  retry.
- Explicit --nvim-profile fell back to auto -- that key does not exist (or is
  incomplete) on the remote; `:SshDevProfiles <dest>` lists usable keys.
- Session not restored -- check that the server exited normally (SIGKILL
  cannot save) and that `restore_session` is true.
- Port collisions -- local/remote ports are deterministic per workspace
  profile; start retries with incremented remote ports automatically.
- Forwards stopped -- the forward tunnel dies with the local nvim
  (:SshDevStop / VimLeavePre, like the session tunnel). Re-open
  :SshDevForward and save (:w); forward.txt persists in the workspace
  profile.
- "cannot forward: local port(s) ... in use" -- another process holds the
  port (a leftover ssh from a crashed nvim can; check "ss -ltn" /
  "netstat -an"). Free it or pick a different local port in forward.txt;
  the previously running forwards keep running. On Windows the pre-check
  can miss an occupied port (libuv binds with SO_REUSEADDR), but the
  verified start still catches it: the new tunnel dies, ssh's bind error
  is reported and the previous forwards are restored.
- forward.txt parse errors -- the save reported the exact lines; nothing
  was uploaded or applied until they are fixed.
- A new variable does not reach a running LSP/terminal -- a process keeps
  the environment it was started with; restart the LSP client / open a new
  terminal. Config-time `vim.env` reads need a server restart
  (:SshDevConnect!). See |sshdev-env|.
- env.txt parse errors -- the save reported the exact lines; nothing was
  uploaded or applied until they are fixed (values are never echoed).
- A removed variable still exists after saving -- the running server was
  started before sshdev exported the key manifest; :SshDevConnect!
  restarts it with the current env.txt.
- Old layout after upgrading -- see |sshdev-layout| (binaries and saved
  sessions are migrated; plugins are reinstalled once).
